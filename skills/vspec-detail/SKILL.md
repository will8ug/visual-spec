# VSpec Detail Skill

Expands requirement details into per-function technical specification documents, turning function lists into implementable, testable specs.

## When to Use

Invoke this skill when:
- A function list exists under `/specs/functions/` (generated by `vspec-new`).
- User runs `/vspec:detail` to generate detailed per-function specifications.
- The team needs RBAC, data permissions, page interaction, backend logic, validation rules, and other detailed specs before implementation.

## Prerequisites

This skill requires artifacts produced by `vspec-new`:
- `/specs/functions/*` — function list (required)
- `/specs/background/*` — requirement analysis (recommended)
- `/specs/flows/*.puml` — business flow diagrams (recommended)
- `/specs/background/scenario_details/` — scenario details (recommended)

If `/specs/functions/` is missing or empty, instruct the user to run `/vspec:new` first.

## What This Skill Defines

- Generate per-function detailed technical specification documents.
- Output structured markdown specs covering RBAC, data permissions, page interactions, backend logic, validation, and more.
- Produce a single-page HTML viewer (`reader.html`) for navigating all generated detail docs.
- This skill does NOT generate prototypes, models, test cases, or implementation code.

## Scope Boundary

This skill ends at detailed specification document generation. After completion, use other skills for later stages:
- `vspec-verify` → data models and runnable prototypes
- `vspec-impl` → backend and frontend code generation
- `vspec-accept` / `vspec-i-test` → test case generation

Do NOT attempt to proceed beyond detailed spec generation within this skill — those stages are handled by separate, purpose-built skills.

## Command

### `/vspec:detail`

Use this command to expand requirement details based on the function list.

Language:
- Read `/scheme.yaml` `selected.language` (supports `en`, `zh`, `ja`; default to `en` if missing/invalid).
- All generated spec documents under `/specs/` must use the selected language consistently (headings, tables, field descriptions, statuses, button names, messages).

Flow:
1. Read the feature/function list from `/specs/functions/*`.
   - You must iterate every function row across all files under `/specs/functions/` (not just core.md), so no module or external-system function is missed.
2. Read supporting artifacts when available: `/specs/background/*`, `/specs/flows/*.puml`, `/specs/background/scenario_details/`, `/specs/background/roles.md`, and existing `/specs/models/*.md` (if any).
3. For each function (page or non-page job), first determine which detail artifacts are actually involved, then only generate those artifacts; do not generate documents for non-involved parts.
   - Coverage requirement: for every function row you iterate, you must generate at least `rbac.md` and `data_permission.md`. If you cannot, output an explicit error and stop (do not silently skip).
   - Step type requirement: you must determine the step type from the function row (e.g. terminal type / page vs backend vs job), and generate the corresponding logic artifacts; do not skip logic:
     - For `Web` / `Mobile` / `Web+Mobile` steps: always generate `page_load.md` and `interaction.md`.
     - For `Backend` steps: always generate `service_logic.md` (service logic: inputs/outputs, rules, states, APIs/events, errors, idempotency).
     - For `Job` steps: always generate `job_logic.md` (job logic: trigger/schedule, data scope, retries/compensation, observability, failure handling).
   - Always generate the baseline docs:
     - `rbac.md`: RBAC permissions down to page areas and controls. See `prompts/rbac.md` for the generation prompt.
     - `data_permission.md`: data permission rules and scope. See `prompts/data_permission.md` for the generation prompt.
   - Page-only (for Web/Mobile/Web+Mobile steps; see corresponding prompt files for generation instructions):
     - `page_load.md`: page loading logic (`prompts/page_load.md`)
     - `interaction.md`: page interaction logic (`prompts/interaction.md`)
     - `validation_matrix.md`: validation logic in matrix format (only for submit-type pages/actions; if the page has no submit/save/approve/reject/cancel/change actions, skip — `prompts/validation_matrix.md`)
     - `post_submit_check.md`: checks after submit (if the page has submit — `prompts/post_submit_check.md`)
     - `post_submit_processing.md`: processing logic after submit (if the page has submit — `prompts/post_submit_processing.md`)
     - `post_submit_navigation.md`: post-submit return and navigation (if the page has submit — `prompts/post_submit_navigation.md`)
   - Conditional (generate only if involved by the current function's logic/scenarios/models/dependencies; see corresponding prompt files):
     - `logging_matrix.md`: operation/audit logging — only when business requires change history retention, compliance audit, or non-repudiation (`prompts/logging_matrix.md`)
     - `decision_matrix.md`: decision matrix for operation availability under each status — if there is a status machine and operations vary by status/role (`prompts/decision_matrix.md`)
     - `notification_matrix.md`: notifications — if there is any notification requirement (`prompts/notification_matrix.md`)
     - `mq.md`: MQ topics/events/message schema/reliability — if there is async events, queues, or cross-system eventing (`prompts/mq.md`)
     - `file_import.md`: file import details — if there is any import entry/requirement (`prompts/file_import.md`)
     - `file_export.md`: file export details — if there is any export entry/requirement (`prompts/file_export.md`)
     - `formula.md`: calculation formulas and metric semantics — if there are any calculations/metrics (`prompts/formula.md`)
     - `expression_tree.md`: expression tree (HTML) — if there is multi-level nested branching logic (`prompts/expression_tree.md`)
     - `code_rules.md`: numbering/code generation rules — if any codes/serial numbers are generated/assigned (`prompts/code_rules.md`)
     - `payment.md`: payment and refund details — if there is any payment/refund/settlement/reconciliation logic (`prompts/payment.md`)
     - `auth.md`: account/login details — if there is any non-SSO login/account/password flow (`prompts/auth.md`)
     - `judgemental_matrix.md`: judgemental matrix for multi-factor logic branching — if 2+ factors jointly decide outcomes (`prompts/judgemental_matrix.md`)
   - Module-level (generate at most once per module, and only if involved; see corresponding prompt files):
     - `timeline.md`: time-axis visualization (HTML) for overall flow impact analysis — only when there is long time-span logic that affects flow decisions (`prompts/timeline.md`)
     - `state_machine.md`: status list + transitions + PlantUML state diagram — overall, not per function (`prompts/state_machine.md`)
     - `nfp.md`: non-functional requirements summary for the module — overall, not per function (`prompts/nfp.md`)
     - `cron_job.md`: scheduled jobs summary for the module — overall, not per function (`prompts/cron_job.md`)
4. Write only the generated (involved) detail documents:
   - Per-function: `/specs/details/<module_slug>/<logic_type>/<function_slug>.(md|html)`
   - Module-level: `/specs/details/<module_slug>/<logic_type>/<module_slug>.(md|html)`
5. Load `prompts/index.md` to generate a single-page viewer `/specs/details/reader.html`:
   - Use the built-in HTML template at `prompts/index.html` (copy verbatim, do not regenerate or rewrite).
   - Left: directory tree based on `/specs/details/`
   - Right: markdown-rendered reading pane
   - Render PlantUML diagrams (do not show raw PlantUML text)
6. Return the generated detail spec summary. STOP. Do NOT proceed to code generation, prototype building, data model creation, or any implementation. The next stages (/vspec:verify, /vspec:impl, etc.) are handled by other skills — the user must invoke them separately when ready.

- `prompts/post_submit_check.md`: checks after submit.
- `prompts/post_submit_processing.md`: processing logic after submit.
- `prompts/post_submit_navigation.md`: post-submit return and navigation.

- `prompts/job_logic.md`: job logic for Job steps (trigger, retries, compensation).
- `prompts/logging_matrix.md`: operation/audit logging.
- `prompts/decision_matrix.md`: decision matrix for status-based operation availability.
- `prompts/notification_matrix.md`: notification requirements.
- `prompts/mq.md`: MQ topics, events, message schema, reliability.
- `prompts/message_queue.md`: message queue design (additional MQ details).
- `prompts/file_import.md`: file import details.
- `prompts/file_export.md`: file export details.
- `prompts/formula.md`: calculation formulas and metric semantics.
- `prompts/expression_tree.md`: expression tree (HTML) for nested branching logic.
- `prompts/code_rules.md`: numbering/code generation rules.
- `prompts/payment.md`: payment and refund details.
- `prompts/auth.md`: account/login details for non-SSO flows.
- `prompts/judgemental_matrix.md`: judgemental matrix for multi-factor logic branching.
- `prompts/timeline.md`: time-axis visualization (HTML) for flow impact analysis.
- `prompts/state_machine.md`: status list, transitions, and PlantUML state diagram.

## Suggested Workflow

1. Ensure `/specs/functions/` exists and is non-empty (run `/vspec:new` first if needed).
2. Run `/vspec:detail`.
3. The skill reads the function list and supporting artifacts.
4. For each function, it determines which detail artifacts apply and generates them.
5. All generated docs are written under `/specs/details/`.
6. A `reader.html` is generated for navigating and reviewing all detail specs.
7. Stop. The detail spec phase is complete. Suggest the user proceed with other skills (vspec-verify, vspec-impl, etc.) for the next stages.

## Output Goal

This skill produces detailed technical specification documents only:

- Per-function RBAC and data permission specs.
- Page interaction, validation, and post-submit logic for UI functions.
- Backend service logic and job logic for non-UI functions.
- Conditional artifacts (logging, notifications, MQ, payments, etc.) as applicable.
- A single-page HTML viewer for navigating all generated detail docs.

Output is limited to `/specs/details/`. No code, models, prototypes, or test cases are generated.
