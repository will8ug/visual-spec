# VSpec Impl Skill

Generates integrated backend and frontend code from detailed specifications, producing structured, reviewable implementation code aligned with the repository's actual tech stack and conventions.

## When to Use

Invoke this skill when:
- Detailed specs exist under `/specs/details/` (generated by `vspec-detail`).
- Data models exist under `/specs/models/` (generated by `vspec-verify`).
- User runs `/vspec:impl` to generate implementation code.
- The team needs a runnable backend project with core APIs and frontend integration code.

## Prerequisites

This skill requires artifacts produced by earlier skills:
- `/specs/functions/*` — function list (required, from `vspec-new`)
- `/specs/details/` — per-function detailed specs (required, from `vspec-detail`)
- `/specs/models/*.md` — data models (required, from `vspec-verify`)
- `/specs/background/dependencies.md` — external dependencies (recommended)
- Repository tech stack and code conventions (auto-detected)

## What This Skill Defines

- Generate a runnable backend project under `/specs/backend/` following the repository's actual stack.
- Produce backend code: health check endpoints, core APIs, services, data access layer.
- Generate frontend integration code under `/specs/prototypes/` after backend APIs are available.
- Follow backend-first approach: backend APIs must be available before frontend integration.
- Validate implementation structure and test coverage post-generation.
- This skill generates **spec-driven implementation code** for review and integration.

## Scope Boundary

This skill generates spec-driven implementation code under `/specs/`. It does NOT:
- Modify existing production code outside of `/specs/`.
- Deploy or release code to production.
- Replace the project's existing codebase — output is contained under `/specs/`.

After completion, use other skills for later stages:
- `vspec-accept` → acceptance test case generation
- `vspec-i-test` → unit and integration test case generation
- `vspec-script` → Playwright automation scripts

## Command

### `/vspec:impl`

Use this command to generate integrated frontend/backend code based on the specs.

Flow:
1. Read `/specs/functions/*`, `/specs/details/`, `/specs/models/*.md`, `/specs/background/dependencies.md`, and detect the current frontend/backend stacks and code conventions.
2. Load `prompts/implement.md` and implement backend-first: generate a runnable backend project under `/specs/backend/` (health check + core APIs/services), then generate frontend integration after backend APIs are available.
3. Write code only under `/specs/` with minimal diffs and keep it reviewable; backend must be under `/specs/backend/` and prototype frontend under `/specs/prototypes/`.
4. Load `prompts/harness/impl/post_impl_verify.md` to validate backend MVC structure and test coverage. If it outputs any issues, show the issue list and stop.
5. Return the generated implementation summary. STOP. The implementation code under `/specs/` is ready for review. For test generation, use `vspec-accept` and `vspec-i-test` separately.

## Prompt Files

- `prompts/implement.md`: the main prompt for generating integrated backend and frontend implementation code.
- `prompts/harness/impl/post_impl_verify.md`: post-implementation verification prompt that validates backend MVC structure and test coverage.

## Suggested Workflow

1. Ensure all prerequisite specs exist under `/specs/` (run `vspec-new` → `vspec-detail` → `vspec-verify` first if needed).
2. Run `/vspec:impl`.
3. The skill detects the repository's tech stack and code conventions.
4. Backend code is generated first under `/specs/backend/`.
5. Frontend integration code follows under `/specs/prototypes/`.
6. Post-implementation verification validates structure and coverage.
7. Review the generated code under `/specs/`. For test generation, proceed with `vspec-accept` or `vspec-i-test`.

## Output Goal

This skill produces spec-driven implementation code:

- A runnable backend project under `/specs/backend/` with health check and core APIs.
- Frontend integration code under `/specs/prototypes/` connected to backend APIs.
- Code that follows the repository's actual tech stack, conventions, and minimal diff principles.

Output is limited to `/specs/backend/` and `/specs/prototypes/`. Code is generated for **review and integration**, not for direct production deployment.
